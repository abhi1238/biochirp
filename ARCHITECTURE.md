# BioChirp architecture

A retrieval system over 11 curated biomedical databases (10 offline parquet snapshots + Open Targets' live GraphQL API), sharing a common entity-resolution and query-planning pipeline. This document maps the components and the request flow between them. For per-DB authoring see [`dbs/README.md`](dbs/README.md).

Everything described here is derived directly from [`docker-compose.yml`](docker-compose.yml) (itself generated by [`scripts/gen_compose.py`](scripts/gen_compose.py) from each `dbs/<db>/manifest.yaml`) — if this document and the compose file ever disagree, the compose file is right.

## High-level shape

```
                              USER QUESTION
                                    │
                                    ▼
┌───────────────────────────────────────────────────────────────────────┐
│  Entry points                                                         │
│  • frontend/db_chat.html?db=<slug>  (per-DB chat UI, 10 offline DBs)  │
│  • frontend/opentarget_api.html     (Open Targets)                    │
│  • MCP server (mcp_server/) — direct tool calls from Claude/agents    │
└────────────────────────────────┬──────────────────────────────────────┘
                                  ▼
                biochirp_orchestrator_tool (8021)
                per-DB router: router_tool / execute_tool /
                expand_and_match_tool / planner_tool / schema_mapper_tool /
                web_tool — HTTP client wrappers around the services below
                                  │
                ┌─────────────────┴─────────────────┐
                ▼                                     ▼
biochirp_expand_and_match_db_tool (8009)    biochirp_schema_mapper_tool (8019)
entity resolution, fans out to:             ANN retrieval over
  synonyms_expander        (8014)           evaluation/schema_kg/inputs/<db>/
  fuzzy_tool                (8013)          schema.json — shared across all 10
  semantic_tool  (8015, GPU-preferred,      offline DBs (heavy embedding model,
    Qdrant-backed dense retrieval)          one instance)
                │                                     │
                │                                     ▼
                │                     biochirp_schema_planner_tool (8020)
                │                     deterministic join/plan assembly from
                │                     the schema_mapper's candidate columns
                │                     (lean, no embedding model)
                └─────────────────┬───────────────────┘
                                  ▼
                    biochirp_<db>_tool  (one per offline DB, built on
                    app/per_db_tool/ — see "Shared per-DB library" below)
                    executes the plan against database/<db>/*.parquet
                                  │
                                  ▼
                    LLM summarization → answer + evidence table
```

Open Targets does not go through this offline path at all — `opentarget_service/` (port 8026) is a standalone service that queries the live Open Targets GraphQL API directly, with its own resolver/entity-extraction/summarization pipeline. It's structurally different from the 10 `app/per_db_tool/`-based services, not a variant of them.

## Directory map

| Path | What lives here |
|---|---|
| `app/per_db_tool/` | Shared library every one of the 10 offline per-DB tool services is built on (mounted read-only into each container) |
| `app/tools/<db>/` | Thin per-DB wrapper: `main.py` (FastAPI app via `build_app()`), `<db>.py` (capabilities/limitations text + `setup_service_globals()` call), `database_loader.py` (reads the parquet snapshot) |
| `app/tools/orchestrator/` | Routes each query through schema_mapper/schema_planner to the target per-DB tool |
| `app/tools/schema_mapper/`, `app/tools/schema_planner/` | The two-stage schema-grounded planner described above |
| `app/tools/expand_and_match_db/`, `expand_synonyms(_unrestricted)/`, `fuzzy/`, `semantic_filter/` | Entity-resolution pipeline |
| `app/tools/planner/`, `readme/`, `share/`, `tavily/` | Supporting/enrichment services |
| `app/services/synonyms/` | Drug/gene/disease synonym lookup tables, used by `expand_synonyms*` |
| `app/utils/` | Shared utilities: dataframe handling, LLM gateway, logging, disclaimers, etc. |
| `opentarget_service/` | Open Targets — standalone live-GraphQL service, not built on `app/per_db_tool/` |
| `mcp_server/` | MCP server (`server.py` stdio, `http_server.py` HTTP/SSE) — runs independently of `docker compose`, deployed separately (see `deploy/`) |
| `dbs/<slug>/manifest.yaml` | Per-DB authoring surface: description, schema, Docker service spec. See [`dbs/README.md`](dbs/README.md) |
| `config/schema.py` | Authoritative joinable schema (planner reads this, not the manifests, for join logic) |
| `config/settings.py`, `guardrail.py`, `provenance.py`, `attributions.py` | Runtime config, request guardrails, provenance stamping, licensing metadata |
| `evaluation/schema_kg/inputs/` | Per-DB schema/queryable/concept-type/rules JSON — the schema_mapper's ANN input and schema_planner's ground truth. Required at runtime (bind-mounted into every per-DB tool + both schema services) |
| `evaluation/schema_kg/src/` | The `schema_kg.src.*` Python modules `schema_planner` imports directly (graph/query/build/rewriter/value_mapper) |
| `resources/prompts/` | Versioned LLM prompts, one per pipeline stage |
| `frontend/` | Static HTML/JS clients |
| `deploy/` | nginx configs + `SECURITY.md` |
| `scripts/` | CI gates (wired into `.github/workflows/`), cache generators (`build_*.py` → `resources/values/*.pkl`), onboarding tooling (`onboard_db.py`, `gen_compose.py`) |

## Shared per-DB library: `app/per_db_tool/`

Every one of the 10 offline-DB containers mounts this library and builds its `main.py` around `build_app()`. Module-by-module:

| Module | Owns |
|---|---|
| `_main.py` | `build_app()` — the FastAPI app factory every `app/tools/<db>/app/main.py` calls |
| `_service_factory.py` | `setup_service_globals()` — wires a DB's `database_loader.py` into the shared pipeline |
| `schema_kg_worker.py` | `SchemaKgConfig`, `make_schema_kg_handler()` — builds the per-DB query handler; also `call_orchestrator()`/`call_web_tool()` |
| `schema_kg_planner.py` | `get_planner()` — wraps `evaluation/schema_kg/src` for this DB |
| `schema_kg_chat.py` | `ChatSpec`, `build_chat_router()` — the chat/WebSocket-facing router |
| `_orchestrator.py` | `WorkerCtx`, `execute_db_query()`, `make_db_result_handler()` — the actual query-execution loop |
| `_finalize.py` | `QueryState`, `finalize_db_result()` — result post-processing before it reaches the summarizer |
| `_schema_guard.py` | `assert_db_schema()` — validates a DB's schema at startup (opted into by hcdt, string) |
| `_text2sql.py` | Generic analytical DuckDB step (COUNT/GROUP BY/threshold queries), reached via a lazy import inside `_orchestrator.py` |
| `db_llm_rules.py` | `load_db_llm_rules()` — loads `resources/prompts/db_llm_rules.yaml`'s per-DB, per-layer LLM nudges |
| `_execute_endpoint.py` | `ExecuteRequest`, `register_execute_endpoint()` — the `/execute` HTTP endpoint (hcdt, string, ttd) |
| `_httpx_client.py`, `_http_session.py`, `_worker_helpers.py` | Shared async/sync HTTP clients and Redis access, used internally by the modules above |

A new DB's `main.py` should follow an existing one as a template — `app/tools/ttd/app/main.py` is a representative example.

## Request lifecycle (offline DB, concrete example)

Question: *"What drugs are used to treat rickets?"* against TTD.

1. `frontend/db_chat.html?db=ttd` opens a WebSocket to `biochirp_ttd_tool`'s chat router (`schema_kg_chat.build_chat_router()`).
2. `schema_kg_worker.make_schema_kg_handler()` runs the query through `expand_and_match_db_tool` (entity resolution) and `schema_mapper_tool` + `schema_planner_tool` (which columns/tables/joins answer this).
3. `_orchestrator.execute_db_query()` executes the resulting plan against `database/ttd/*.parquet`, with `_text2sql.py`'s analytical step available as a fallback for count/aggregate-style questions.
4. `_finalize.finalize_db_result()` post-processes the result table.
5. The summarizer (prompt selected by `SYNTHESIZER_MODE` — `resources/prompts/synthesizer.md` for narrative prose, `synthesizer_eval.md` for terse benchmark-scorable output) turns the table into a grounded answer.
6. The chat router streams tool-call events and the final answer back over the WebSocket.

Open Targets follows a parallel but separate path entirely inside `opentarget_service/`: entity extraction → GraphQL resolvers (`resolvers.py`, `disease_data.py`, `target_data.py`) → its own summarization step.
